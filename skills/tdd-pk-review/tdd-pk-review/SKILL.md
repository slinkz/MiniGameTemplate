# 技术文档对抗评审（PK Review）

## 概述

通过 **攻方（Attacker）** 和 **守方（Defender）** 两个专家角色的结构化多轮对抗，系统性发现技术文档中的设计缺陷、遗漏和风险。**PM** 作为流程调度者，控制轮次节奏和收敛判定。

## 触发条件

以下场景触发此技能：
- 用户要求对技术文档进行 PK 评审 / 对抗评审
- 用户要求"帮我审一下这个设计"或类似表述
- 用户提供了 TDD / ADR / API 设计文档并要求评审

## 核心流程

```
┌─────────────┐
│  Phase 0    │  PM 收集输入：目标文档、角色配置、代码路径（可选）
│  准备       │  → 创建 PK 记录文件（Question.md）
└──────┬──────┘
       ▼
┌─────────────┐
│  Phase 1    │  攻方阅读文档（+ 代码）→ 输出结构化问题（带严重度）
│  攻方提问   │  → 写入 PK 记录文件
└──────┬──────┘
       ▼
┌─────────────┐
│  Phase 2    │  守方逐一回应 → 更新目标文档 → 更新 PK 记录
│  守方回应   │  → 文档版本号递增
└──────┬──────┘
       ▼
┌─────────────┐
│  Phase 3    │  PM 判定收敛：严重度趋势 + 阻塞项数量
│  收敛判定   │  → 收敛则结束，否则回到 Phase 1
└──────┬──────┘
       ▼
┌─────────────┐
│  Phase 4    │  输出 PK 总结报告 + 更新文档最终版本
│  总结收尾   │
└─────────────┘
```

## 输入参数

在启动 PK 前，收集以下信息（加粗为必填）：

| 参数 | 必填 | 默认值 | 说明 |
|------|------|--------|------|
| **目标文档路径** | ✅ | — | 待评审的 .md 文档路径 |
| **文档类型** | ✅ | TDD | TDD / ADR / API / 系统设计 / 其他 |
| 攻方角色 | — | Unity 架构师 | 攻方专家身份和专长领域描述 |
| 守方角色 | — | 软件架构师 | 守方专家身份和专长领域描述 |
| 代码路径列表 | — | — | 攻方需要阅读的代码文件路径（技术文档必须提供） |
| PK 记录路径 | — | 目标文档同目录/Question.md | PK 记录文件存放位置 |
| 最大轮次 | — | 3 | 超过此轮次强制收敛 |

### 文档类型与代码审查规则

| 文档类型 | 代码审查 | 说明 |
|---------|---------|------|
| TDD（技术设计文档） | **必须** | 攻方必须阅读相关代码验证可行性 |
| ADR（架构决策记录） | **必须** | 需要验证决策与现有代码的兼容性 |
| API 设计文档 | 推荐 | 如有现有实现则需要阅读 |
| 系统设计文档 | 可选 | 早期设计可能还没有代码 |

## Phase 0：准备

1. 确认目标文档存在且可读
2. 如未指定角色，使用默认值（Unity 架构师 vs 软件架构师）
3. 在 PK 记录路径创建 Question.md，使用 `assets/question-template.md` 中的模板格式
4. 如果文档类型要求代码审查但未提供代码路径：
   - 主动在项目中搜索与文档相关的代码文件
   - 如果实在找不到，警告用户并继续（降低攻方审查深度）

## Phase 1：攻方提问

使用 `references/attacker-prompt-template.md` 中的 Prompt 模板，派出**攻方 Agent**（通过 code-explorer subagent）。

攻方 Agent 的任务：
1. 完整阅读目标文档
2. 阅读代码文件（如提供）
3. 如果是 Round 2+，先阅读 Question.md 中上一轮的回应，评估满意度
4. 输出结构化问题列表

**攻方输出格式要求**（每个问题）：
```markdown
## [ID] | 严重度 🔴高/🟡中/🟢低 | 标题
**涉及章节**：§X.X
**质疑**：[具体的技术问题描述]
**潜在风险**：[为什么这是个问题]
**建议方向**：[建议怎么处理]
```

严重度定义：
- 🔴 **高**：阻塞编码/实施，不解决无法开始
- 🟡 **中**：不阻塞但可能导致返工，建议在实施前解决
- 🟢 **低**：改善建议，可在实施期间迭代解决

**攻方行为约束**（写入 Prompt）：
- 只提**有价值**的新问题——不为提问而提问
- Round 2+ 不重复已解决的问题
- 区分"阻塞编码的问题"和"可以编码期间迭代的小问题"
- 只负责提问，不修改任何文件

完成后，将攻方输出写入 Question.md。

## Phase 2：守方回应

PM 直接承担守方角色（无需额外 Agent），逐一回应攻方问题：

1. 分析每个问题的合理性
2. 对合理的问题：
   - 更新目标文档（修正/补充/澄清）
   - 文档版本号递增（如 v2.1 → v2.2）
   - 在 Question.md 中更新问题状态为 ✅ 已回应 + 回应摘要
3. 对不合理的问题：
   - 在 Question.md 中说明拒绝理由
   - 状态标记为 ❌ 已拒绝（附理由）

## Phase 3：收敛判定

参考 `references/convergence-criteria.md` 中的详细标准。

快速判定规则：
1. **🔴高优问题数 = 0** 且 **严重度呈下降趋势** → 收敛
2. **攻方明确表态"无新问题"或"可以收敛"** → 收敛
3. **达到最大轮次** → 强制收敛（记录未解决项）
4. 否则 → 回到 Phase 1

## Phase 4：总结收尾

1. 在 Question.md 底部写入 **PK 总结报告**：
   - 总轮次、总问题数、各严重度分布
   - 最有价值的 Top 3 变更
   - 最终文档版本号
   - 是否有遗留项（标注优先级）
2. 更新目标文档的状态标记为"PK 收敛"
3. 输出一段简洁的总结给用户

## 关键原则

### 不镀金原则
攻方不应为了显示专业而提出过度复杂的问题。目标是让文档"足够好可以开始实施"，而不是追求完美文档。

### 严重度诚实原则
不夸大也不淡化问题严重度。🔴 意味着"不解决就不能写代码"，要对这个判断负责。

### 单一职责
- 攻方只提问，不修改文件
- 守方负责回应和更新文档
- PM 负责流程调度和收敛判定

### 文档自包含
PK 结束后，目标文档和 Question.md 应该能让任何人（包括未参与 PK 的人）理解全部上下文。不允许出现"与 v1.0 相同不再赘述"这样的外部引用。
