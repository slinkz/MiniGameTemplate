## Round 1 — 攻方提问

### DE-R4-001 | 严重度 🟡中 | TDD_05 技能 CD 尺寸与 GDD 不一致

**涉及章节**：TDD_05 §S5.4 HUD 组件规格表 vs GDD_05 §11.1
**质疑**：TDD_05 HUD 组件规格表中 SkillCDIndicator 尺寸标注为"48×48pt"（来自 PK-R3 UID-002），但 GDD_05 §11.1 最新描述仍为"36×36pt"。两处文档数值矛盾，开发者无法确定应以哪个为准。
**潜在风险**：实施阶段按 36pt 开发 → 后期发现需改 48pt → UI 重做。或反之。
**建议方向**：确认最终尺寸并同步 GDD_05 §11.1，或明确 TDD 优先级覆盖 GDD 的声明。

---

### DE-R4-002 | 严重度 🟡中 | TDD_05 布局从 1行×6列改为 2行×3列，GDD 未同步

**涉及章节**：TDD_05 §S5.4 vs GDD_05 §11.1 CD 指示器规格
**质疑**：TDD_05 明确写了"2行×3列居中"（PK-R3 UID-002），但 GDD_05 §11.1 仍描述"横排居中""总宽度 36×6 + 6×5 = 246pt"的单行布局。布局方式的根本分歧（单行 vs 双行）直接影响空间分配和弹幕可视区高度。
**潜在风险**：GDD 的"弹幕可视区 ~65%"计算基于单行 CD 栏（52pt 高），双行将变为 ~100pt 高 → 可视区压缩 ~3%。
**建议方向**：GDD_05 §11.1 应同步更新为双行布局，并重新计算空间分配。

---

### DE-R4-003 | 严重度 🟡中 | TDD_05 被动指示器 40pt 方形圆角 vs GDD"32pt 边框渐变充能动画"

**涉及章节**：TDD_05 §S5.4 vs GDD_05 §11.1 + GDD_02 §4.1
**质疑**：TDD_05 标注被动为"40×40pt 方形圆角(r=8)"，GDD_05 §11.1 组件表写"被动技能栏...左上角（常规）...边框渐变充能动画"但未指定尺寸变更，GDD_02 §4.1 原描述"32pt"。同时 TDD 引入"环形进度条消耗"作为 Active 态，而 GDD 写"左下角小数字倒计时"。
**潜在风险**：实现人员可能按 GDD 使用数字倒计时（更简单），而非 TDD 的环形进度条（更精致但开发更复杂）。
**建议方向**：GDD_02 被动 CD UI 表达章节应更新尺寸和 Active 态描述，或 TDD 附注"本章节覆盖 GDD 原始描述"。

---

### DE-R4-004 | 严重度 🔴高 | TDD_03 DotSlot 数组大小 8 vs GDD 写 16

**涉及章节**：TDD_03 §S3.1 vs GDD_02 §6.2 / §5.1
**质疑**：GDD_02 明确写`DotSlot[16] _dots`（v2.2 扩容），但 TDD_03 §S3.1 写`DotSlot[8] _dots`且注释"V2 最多 3 种同时生效"。这是一个**数据容量不一致**——如果未来 V3 需要更多 DOT 类型，TDD 实施方案将导致不必要的限制。
**潜在风险**：按 TDD 实施 DotSlot[8]，V3 来了发现不够 → 需要改数组大小、可能影响序列化兼容。
**建议方向**：TDD_03 应与 GDD 保持一致使用 DotSlot[16]，理由同 BuffSlot 扩容（统一策略，预留充足）。

---

### DE-R4-005 | 严重度 🟡中 | TDD_01 首次开火延迟从"进入屏幕"还是"BattleStartSequence 结束"

**涉及章节**：TDD_01 §S1.2 验收方案 B4 vs TDD_01 §S1.1 关键约束
**质疑**：TDD_01 §S1.1 关键约束明确写"FirstAttackDelay 起算时刻：从 BattleStartSequence 结束（Time.timeScale=1）后开始计算"，但 §S1.2 验收方案 B4 仍写"计时从敌机进入屏幕到首次射击"。两者矛盾——如果起算是全局的（从 timeScale=1 起），那验收方案的"进入屏幕"描述就是错的；如果是每只敌机各自的，那 §S1.1 的措辞就有歧义。
**潜在风险**：开发者理解为"全局计时"导致后续波次的敌机出场即开火（已经过了全局 firstDelay）。
**建议方向**：明确 FirstAttackDelay 是**每只敌机各自独立**的计时器（从该敌机 Spawn 时刻开始），而"BattleStartSequence 结束"是指**第一波敌机的 Spawn 时刻**不会在 timeScale=0 期间发生。验收方案需统一措辞。

---

### DE-R4-006 | 严重度 🟢低 | TDD_02 Buff 道具命名 vs GDD SO 一览不一致

**涉及章节**：TDD_02 §S2.4 创建 SO 资产 vs GDD_03 §8.1 SO 资产一览
**质疑**：TDD_02 写"SG_Pickup_Buff_SpeedUp / SG_Pickup_Buff_AttackUp"，但 GDD_03 §8.1 SO 一览只列了"SG_Pickup_Buff_SpeedUp"且后面用省略号标注"~8"。GDD §7.2 道具类型表中 Buff 道具只提到"获得一个临时增益 Buff"泛指，没有逐个列出。TDD 比 GDD 更具体（多列了 AttackUp），但名称"AttackUp"对应哪个 BuffConfigSO 不明确——GDD 中疾风(1001)的效果是 AttackInterval×0.5（攻速），而不是"攻击力增加"。
**潜在风险**：命名误导——"AttackUp"暗示攻击力增加，但实际上是攻速增加（疾风效果）。
**建议方向**：统一命名为 `SG_Pickup_Buff_Zephyr`（疾风对应）或明确 TDD 注释"AttackUp = 疾风 BuffId=1001"。

---

### DE-R4-007 | 严重度 🟡中 | GDD "首波不做特殊动效" vs TDD "首波也执行弹跳"

**涉及章节**：GDD_05 §11.1 波次过渡动效 vs TDD_05 §S5.4 WaveIndicator
**质疑**：GDD_05 波次过渡动效明确写"首波（开场）：不做特殊动效——直接进入战斗，避免打断新手的'发现'体验"。但 TDD_05 §S5.4 WaveIndicator 写"首波也执行弹跳（PK-R3 UID-010 取消'首波无动效'限制）"。这是 PK-R3 UI 设计师提出的变更，但**GDD 未同步更新**。
**潜在风险**：GDD 是设计权威，如果策划按 GDD 审查发现 TDD 与之矛盾，可能要求回退。
**建议方向**：GDD_05 §11.1 波次过渡动效"首波"行需要同步更新为"PK-R3 变更：首波也执行弹跳（因为有 BattleStartSequence 过渡，不会打断体验）"。

---

### DE-R4-008 | 严重度 🟢低 | TDD_04 S4.3 damageStats 用 Dictionary 但 TDD_01 说"sourceTag 用 int[] 托管数组"

**涉及章节**：TDD_04 §S4.3 vs TDD_01 §S1.3（内部一致性）
**质疑**：TDD_04 §S4.3 写"`Dictionary<int, int> _damageStats`"作为统计容器，同时 BulletWorld 用"`int[] _sourceTags`"存储每弹丸来源。这本身没问题。但 TDD_04 的 DamageDealer 采集逻辑写"`_damageStats[context.SourceId] += context.FinalDamage`"——当 SourceId 包含 DOT Id（如 4001）时，Dictionary key 范围跳跃很大（0~7 + 4001~4003），虽然功能正确，但遍历输出时排序可能不直观。
**潜在风险**：次要。统计结果展示到 UI 时需要额外的 key→显示名映射逻辑，TDD 未描述此映射。
**建议方向**：TDD_05 结算面板（VictoryPanel）的技能贡献展示应补充"sourceTag→技能名称/图标映射"的配置方案（建议使用一个 static 或 SO 映射表）。

### DE-R4-004 | ✅ 已回应（接受——TDD DotSlot 扩容到 16）

**分析**：攻方指出 GDD_02 §5.1/§6.2 写 `DotSlot[16]`（v2.2 扩容），但 TDD_03 §S3.1 写 `DotSlot[8]`。需要区分两个概念：
- **BuffSlot[16]**：天命人决策从 8→16，GDD 和 TDD 已同步 ✅
- **DotSlot[8]**：TDD 独立设置了 8，与 GDD 不一致

**权衡**：
- DotSlot[8] 的理由是"V2 最多 3 种 DOT"，8 已有余量
- 但 GDD 统一扩容策略是 16，保持一致性更重要——避免 V3 需要改大小
- 16 个 DotSlot 额外内存：~16 × sizeof(DotSlot) ≈ 几百字节，完全可忽略

**处理**：
1. ✅ TDD_03 §S3.1 DotSlot[8] → DotSlot[16]，与 GDD 保持一致
2. ✅ 注释更新："V2 最多 3 种同时生效，16 为统一扩容预留"

### DE-R4-005 | ✅ 已回应（接受——统一措辞）

**分析**：攻方精准地指出了一个措辞歧义：
- §S1.1 关键约束写"从 BattleStartSequence 结束后开始计算"——听起来像**全局计时**
- §S1.2 验收 B4 写"计时从敌机进入屏幕"——听起来像**个体计时**

实际设计意图是：**每只敌机各自独立的 FirstFireDelay，从该敌机 Spawn 时刻开始**。"BattleStartSequence 结束"的约束含义是：**第一波敌机的 Spawn 不会发生在 timeScale=0 期间**，因此 FirstFireDelay 不会在 BattleStartSequence 期间空跑。

**处理**：
1. ✅ TDD_01 §S1.1 关键约束改措辞："FirstAttackDelay 是**每只敌机各自独立**的计时器，从该敌机 Spawn 时刻开始计算。注：因为 EntitySpawner 在 BattleStartSequence 结束（timeScale=1）后才启动，第一波的 Spawn 不会发生在 timeScale=0 期间。"
2. ✅ TDD_01 §S1.2 验收 B4 改措辞："计时从该敌机 Spawn 时刻到首次射击"
