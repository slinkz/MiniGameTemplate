> **来源**：借鉴 OpenSpec 规范驱动开发（SDD）的核心思想，适配本项目现有 TDD + ADR 体系。
> **生效日期**：2026-04-21
> **原则**：零工具依赖，仅通过文档写法约定提升规范一致性和可维护性。

### 规则 1：TDD 活文档 — 单一信息源

**问题**：TDD 在 PK 评审后趋于"冻结"，后续变更通过 ADR 追加，导致"系统当前支持什么"散落在 TDD + 多个 ADR + 验收报告中，无单一信息源。

**规则**：每次 ADR 落地实施后，**同步更新 TDD 对应章节的 AC 状态**。TDD 始终反映系统的当前行为。

**格式**：在 TDD 的 AC/功能列表中维护 `状态` 和 `变更记录` 两列：

```markdown
| AC    | 描述                        | 状态           | 变更记录  |
|-------|-----------------------------|----------------|----------|
| AC-01 | Bullet 走 RuntimeAtlas      | ✅ Implemented | ADR-028  |
| AC-02 | 多 VFX 类型共存 Atlas        | ⏸ 暂缓        | —        |
| AC-13 | Laser Atlas 接入            | ✅ Implemented | ADR-031  |
| AC-14 | new Material() keyword 规范  | ✅ 铁律        | ADR-032  |
```

**状态枚举**：
- `✅ Implemented` — 已实施并验收通过
- `✅ 铁律` — 已提升为项目级强制规范
- `⏸ 暂缓` — 有意推迟，记录原因
- `❌ 废弃` — 不再需要，记录原因和替代方案
- `🔄 修改` — 原始定义已变更，见关联 ADR

**[AGENT] 执行时机**：完成 ADR 写入后，紧接着更新 TDD 中的对应 AC 状态行。两个操作在同一个工作单元内完成，不允许"以后再补"。

### 规则 2：变更包归档 — 一个文件还原全貌

**问题**：重大功能/修复完成后，相关信息散布在 Git log、ADR、日志、MEMORY.md 多处，事后回溯需要拼图式还原。

**规则**：每个重大功能或修复闭环后，在 `docs/Agent/changes/` 下创建归档文件夹，包含一页纸总结。

**目录结构**：

```
docs/Agent/changes/
└── YYYY-MM-DD-<变更简称>/
    ├── SUMMARY.md          ← 一页纸总结（必须）
    ├── commits.txt         ← 关联 Git commit hash 列表（必须）
    └── review-notes.md     ← CR/PK 评审要点（可选）
```

**SUMMARY.md 模板**：

```markdown
# <变更标题>

## 动机
<!-- 1-2 句话：解决什么问题 / 为什么要做 -->

## 变更范围
<!-- 列出改动的模块和文件（高层描述，不需逐行） -->

## 关键决策
<!-- 列出本次变更中的重要技术选择，引用 ADR 编号 -->

## 行为变化
<!-- 用户/系统可感知的行为变化，对应 TDD 中的 AC 编号 -->

## 已知遗留
<!-- 本次未处理的问题或后续待办（如有） -->

## 关联
- ADR: ADR-0xx
- Commits: abc1234, def5678
- 前置变更: YYYY-MM-DD-<前置变更名>（如有）
```

**[AGENT] 触发条件**：以下情况必须创建变更包：
1. 功能涉及 **3 个及以上文件** 的修改
2. 产生了新的 **ADR 记录**
3. 经过了 **PK 评审** 或 **正式 CR 评审**

不满足以上任一条件的小改动（typo 修复、单文件 bug fix 等）不需要创建变更包。

### 规则 3：行为契约与实现分层 — 验收和维护各看各的

**问题**：TDD 中验收标准（AC）和技术实现细节混在一起写，导致实现变更时分不清"哪些还有效，哪些已过时"。

**规则**：TDD 中每个功能模块按 **行为契约**（稳定层）和 **技术方案**（易变层）两层书写。

**格式**：

```markdown
## <功能名称>

### 行为契约（稳定层）
<!-- 描述"系统做什么"——面向验收，不涉及实现细节 -->
<!-- 使用 BC-xx 编号，变更需走 ADR -->
- **BC-01**: <可验证的行为描述>
- **BC-02**: <可验证的行为描述>

### 技术方案（易变层）
<!-- 描述"怎么实现的"——面向开发/维护，随实现演进 -->
<!-- 变更后更新此区域 + 标注关联 ADR -->
- <实现细节 A>
- <实现细节 B>（ADR-0xx）
```

**分层原则**：

| 层级 | 内容 | 变更频率 | 谁看 |
|------|------|---------|------|
| **行为契约** | 系统可观测行为、验收标准、性能门槛 | 低（需 ADR 审批） | 验收者、测试者 |
| **技术方案** | 类名、方法签名、Shader keyword、数据结构 | 高（随实现演进） | 开发者、维护者 |

**判断标准**：如果一条描述在"换一种实现方式"后仍然成立，它属于行为契约；如果会失效，它属于技术方案。

**示例**：
- "Atlas 模式下 DC 不增加" → **行为契约**（不管怎么实现，DC 不能增加）
- "LaserRenderer 创建 Atlas Material 克隆并 EnableKeyword" → **技术方案**（换了实现方式这条就过时了）

**[AGENT] 适用时机**：
- **新功能**：TDD 初始撰写时直接分层
- **存量功能**：下次碰到该模块做修改时顺手重构为分层格式，不需要一次性全改

---

### 三条规则的协作关系

```
规则 3（分层书写）→ TDD 结构清晰
          ↓
规则 1（活文档）  → TDD 始终是当前状态的单一信息源
          ↓
规则 2（变更包）  → 每次重大变更的完整上下文可追溯
```

**核心收益**：任何新会话开局，读 TDD 就知道"系统现在能做什么"；读变更包就知道"上次改了什么、为什么改"；读行为契约就知道"该测什么"；读技术方案就知道"怎么改"。
