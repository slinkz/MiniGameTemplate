## PK Round 1 — 攻方提问

### PT-001 🔴 工具 P0 工时 2.5h 但依赖 BattleController 编译完成——循环依赖未标注
**文档位置**：INDEX §工具总览与优先级  
**问题**：工具 P0 包含 5 个 Debug MenuItem（引用 `BattleController.RetryBattle` / `DebugForceVictory`）+ ProfilerMarker（在 BattleController 中）+ BaseLineY Gizmo（在 BattleController.OnDrawGizmos 中）。这些全部**直接嵌入 BattleController 类**或**引用其方法**——意味着必须等核心 TDD 的 SG-P0 先完成。  
**但 INDEX 把工具 P0 和核心 P0 标为同级 P0**，暗示可以并行——实际不行。  
**建议**：在工具 INDEX 中明确标注"依赖核心 SG-P0.2 完成后方可开始"，或将工具 P0 改名为 SG-P0.5（夹在核心 P0 和 P1 之间）。

---

### PT-002 🔴 验收标准 #8 "非 Play Mode 全部灰显"——缺少具体验证步骤
**文档位置**：TOOLS_TDD_02 §8 验收标准  
**问题**：验收项 #8 只说"非 Play Mode 时全部灰显不可点击"，但没有说：(1) 开发者如何验证灰显（需要退出 PlayMode 后在菜单栏检查）；(2) 如果 Validate 方法有 bug（返回 true），开发者如何发现问题。实际上灰显测试经常被跳过因为"太显而易见"然后发布时发现 Play Mode 外误触。  
**建议**：验收 #8 改为"明确步骤：退出 Play Mode → 打开 Tools/SG/Debug 菜单 → 确认所有 5 项灰显不可点击 → 截图存证"。

---

### PT-003 🟡 SG_EditorUtility.FindSOByName 的性能假设未验证
**文档位置**：TOOLS_TDD_02 §2.1  
**问题**：`AssetDatabase.FindAssets()` 在大项目中可能耗时（扫描全 Assets），且这个工具在 OnEnable + CacheSOs 时调用 6 次。当前项目小（~800 文件）没问题，但文档应标注假设边界。如果以后 SO 增多到数百个，FirstOrDefault 匹配可能出错（名字子串匹配）。  
**建议**：  
1. 在 FindSOByName 注释中标注"假设项目 SO 规模 < 100，否则需换方案"  
2. 搜索用精确名 `t:FloatVariable SG_BaseHP`，当前实现是子串匹配可能匹配到 `SG_BaseHP_v2`

---

### PT-004 🟡 SkipToNextWave 的验收——"等待下一波推进"如何验证？
**文档位置**：TOOLS_TDD_02 §2.1 SkipToNextWave  
**问题**：Debug.Log 说"已秒杀全部敌机，等待下一波推进"——但开发者如何确认下一波真的推进了？需要看 `SG_CurrentWaveIndex` SO 变量增加了吗？还是看 Scene 中新敌机出现了？如果 AllCleared 判定有 1 帧延迟，开发者可能以为功能坏了。  
**建议**：在 SkipToNextWave 末尾补充 EditorCoroutineUtility.StartCoroutineOwnerless 做 1 帧延迟检查并 Log 确认"✅ 波次已推进到 N+1"。或在验收标准中明确"等待 0.1s 后观察 SG_CurrentWaveIndex +1"。

---

### PT-005 🟡 FairyGUI 校验工具 P2 降级——但 TDD 已写了完整代码（~80 行）
**文档位置**：TOOLS_TDD_02 §5  
**问题**：§5 标注为"P2 — Backlog"，但已经写了完整的类设计和代码实现。从 PM 视角，这产生两个问题：  
1. 开发者可能误以为"代码都写好了我应该实现它"——浪费时间在 V1 中做 P2  
2. V2 回来时这段代码可能已过期（FairyGUI XML 结构变了）  
**建议**：要么删除完整代码只保留需求描述（3 行足矣），要么标注为"参考实现草案，V2 时需重新适配"。

---

### PT-006 🟡 "一键复制最后一波"的验收 #5 公式假设 Timer 模式——与 V1 铁律矛盾
**文档位置**：TOOLS_TDD_01 §4 + §5 验收标准  
**问题**：验收标准 #5 说"新波次 TriggerDelay = 源 Delay + 源预估时长 + 3s"。但核心 TDD PM-008 V1 铁律确认"5 关全用 AllCleared 模式"。在 AllCleared 模式下，CalculateNewDelay 直接返回源值不自动递增（代码第 207-208 行）。**验收标准写的公式只适用于 Timer 模式**——V1 中实际验证时永远不会触发。  
**建议**：  
1. 验收 #5 改为"AllCleared 模式：新 TriggerDelay = 源 TriggerDelay（不递增）"  
2. 或拆为两条：一条 AllCleared（保持不变）+ 一条 Timer（+3s 递增）

---

### PT-007 🟡 统计面板工时 0.5h——但代码已包含完整的 Timer/AllCleared 分支逻辑（~70 行）
**文档位置**：INDEX §工具总览  
**问题**：DrawStatisticsPanel 的代码有 70+ 行含条件分支（Timer 波/AllCleared 波的时长区分），0.5h 实现含编译验证是紧凑的。如果开发者不是直接照抄代码而是"按设计实现"，加上测试多种波次配置，实际需要 45-60min。  
**建议**：工时 0.5h → 0.75h。虽然小差异，但 PM 的工时表需要诚实。

---

### PT-008 🟡 子弹识别逻辑 (AT-010) 靠 "没有 HealthComponent" 来判断——脆弱假设
**文档位置**：TOOLS_TDD_02 §4.2 Entity 统计  
**问题**：`bool isBullet = e.GetComponent(ComponentType.Health) == null && e.Camp != EnumCamp.Neutral;` 这个判断依赖"子弹没有 HealthComponent"的假设。如果未来加了可被打掉的子弹（有 HP 的弹幕），统计就会出错。从 PM 视角——文档应标注这个假设的边界。  
**建议**：在代码注释中明确"V1 假设：子弹 = 无 HealthComponent 的非中立 Entity。V2 如有 HP 子弹需改用 EntityTag 判断。"

---

### PT-009 🟢 SG_SpawnWaveSOEditor 的验收 #4 "深拷贝修改不影响源"——如何手动验证？
**文档位置**：TOOLS_TDD_01 §5 验收标准  
**问题**：验收 #4 说"修改不影响源"——开发者如何高效验证？修改新波次 Group.Count、然后检查源波次 Count 没变？需要步骤提示。小问题但新手开发者可能不知道怎么验。  
**建议**：验收 #4 补充"修改新波次第一个 Group 的 Count+1 → Ctrl+Z 撤销 → 确认源波次未被修改"。

---

### PT-010 🟢 工具 P1 "飘字坐标 Debug.DrawLine" 只有 3 行代码但占工时 15min
**文档位置**：INDEX §工具总览  
**问题**：3 行代码的 Debug.DrawLine 估 15min——含"理解坐标系+确认 worldPos 正确"的时间。实际只要飘字功能本身已完成（P3.3），这个 Debug 补丁是 2 分钟的事。15min 是合理的"含上下文理解"估算，但从实施看这不需要独立子任务。  
**建议**：合并到核心 TDD P3.3 的 BattleHUDController 实现中，不需要单独列为工具任务。
