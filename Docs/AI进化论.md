# AI 进化论

> **这份文档记录天命人如何将一个普通的 AI 助手，逐步锻造为深度绑定项目的高效协作伙伴。**
> 每一次"进化"都来自实践中的痛点，而非理论推演。

---

## 进化时间线

### Epoch 0：项目诞生（2026-04-05）

**状态**：AI = 通用问答机器，对项目一无所知。

| 事件 | 提交 | 影响 |
|------|------|------|
| 项目初始化 | `0dfe833` | UnityProj + UIProject + Docs 三分天下 |
| 首次多维度审查 | `7533e86` ~ `64fda4c` | 编辑器/架构/性能/安全 4 轮审查，共修复 58 项问题 |

**复盘**：AI 能力原始但有用——给它明确的审查维度，它就能系统性扫描。但它没有记忆，每次都要重新理解项目。

---

### Epoch 1：文档双轨制（2026-04-05）

**痛点**：文档写给谁？人类看不懂机器格式，AI 消化不了散文体。

**进化**：将 `Docs/` 拆分为 `Agent/`（机器可检索）和 `Guide/`（人类可读）。

| 事件 | 提交 | 影响 |
|------|------|------|
| Docs 分为 Agent/ + Guide/ | `869a484` | 各自用最适合的格式服务各自的读者 |

**经验**：**双轨制解决了"给谁看"的问题**——Agent 文档追求结构化/可搜索/字段级精确，人类文档追求叙事连贯/图文并茂。

---

### Epoch 2：首个 Skill 诞生（2026-04-06）

**痛点**：AI 每次操作配置表都要被重新教一遍 Luban 的规则。

**进化**：创建第一个 Skill —— `luban-config`，将 SOP 和脚本固化为可重复加载的专家知识包。

| 事件 | 提交 | 影响 |
|------|------|------|
| luban-config Skill 创建 | `04cfc79` | SOP + 自动化脚本一体化，AI 再也不会忘记 Luban 的规矩 |

**经验**：**Skill = 可加载的专家记忆**。把反复教的东西固化成 Skill，AI 就不再是健忘的助手。

---

### Epoch 3：PK 对抗评审制度（2026-04-11 ~ 04-27）

**痛点**：AI 写文档时容易自嗨——自己写自己审，漏洞全被自己"合理化"了。

**进化**：创建 `tdd-pk-review` Skill，引入"攻方 vs 守方"的多 Agent 对抗机制。通过角色分离制造有益的对抗张力。

| 事件 | 关键验证 | 影响 |
|------|---------|------|
| Entity-Component TDD 6 轮 PK | `Archive/EntityComponent/PK*` | 118 个问题 / 100% 收敛 |
| ShooterGame GDD/TDD 11+ 轮 PK | `SG_*_PK*.md` 系列 | 多角色（架构师/PM/工具开发者/微信专家）交叉攻击 |

**经验**：**PK 让 AI 无法自说自话。** 攻方负责挑刺，守方负责回应修改，PM 控制收敛——三权分立让文档质量可证伪。

---

### Epoch 4：任务面板系统（2026-04-18）

**痛点**：复杂项目有几十个并行/串行任务，跨会话后 AI 完全忘了进度在哪。

**进化**：参考 OpenSpecs 设计理念，创建 `task-tracker` Skill + `.tasks/BOARD.md` 看板。

| 事件 | 产出 | 影响 |
|------|------|------|
| task-tracker Skill 创建 | `.tasks/` 目录体系 | 跨会话任务状态零丢失 |
| BOARD.md 看板 | 唯一入口点 | 新会话 30s 内恢复全部上下文 |

**经验**：**Working memory 不可靠，文件系统才是真相。** 把任务状态落盘到磁盘，AI 的"记忆力"就跟文件系统一样持久。

---

### Epoch 5：Unity MCP 接入（2026-05-03 ~ 05-04）

**痛点**：AI 写代码后无法验证是否能编译通过，需要人工 Alt-Tab 到 Unity 去看。

**进化**：接入 `com.anklebreaker.unity-mcp` 包，让 AI 可以直接操控 Unity Editor——编译检查、执行代码、截图、Play Mode 控制。

| 事件 | 产出 | 影响 |
|------|------|------|
| Unity MCP Bridge 安装 | `Packages/com.anklebreaker.unity-mcp` | AI 自己编译验证，不再需要人工中转 |
| TOOLS/MCP_INTEGRATION.md 文档 | `Docs/Agent/TOOLS/MCP_INTEGRATION.md` | 建立使用规范（端口不固定、execute_code 不支持 using 等） |

**经验**：**给 AI 工具而非答案。** MCP 让 AI 能自己"看到"Unity 的状态，而不是猜测或等人类反馈。闭环效率翻倍。

---

### Epoch 6：文档拆分与三路由表（2026-05-02）

**痛点**：文档越写越长，单个文件超 1000 行。AI 加载整个文件浪费 token，还经常找不到需要的部分。

**进化**：
1. 超 400 行的文档强制拆分为 INDEX + 子文件
2. 创建 `INDEX.md` 三路由表：A=任务路由 / B=代码→文档映射 / C=概念速查
3. `doc-maintenance` Skill 固化拆分/归档/行数纪律

| 事件 | 提交 | 影响 |
|------|------|------|
| 文档大规模拆分重构 | 多个 commit | EC_TDD（1文件→8文件）、CONV（1→4）、ATLAS_TDD（1→3）等 |
| doc-maintenance Skill 创建 | — | R1~R9 规则让文档维护有章可循 |
| INDEX.md 三路由表 | — | AI 一步到位找到目标文件，不再盲目 grep |

**经验**：**文档结构 = AI 的导航系统。** 没有索引的文档堆积就像没有路标的城市——再好的内容也找不到。

---

### Epoch 7：Skill 体系规模化（2026-04 ~ 05）

**痛点**：随着项目深入，需要固化的知识越来越多。单靠记忆放不下，单靠文档又太被动。

**进化**：建立 8 个 Skill 形成完整的知识矩阵：

| Skill | 定位 | 解决的问题 |
|-------|------|-----------|
| `coding-standards` | 编码前加载 | "怎么写"的铁律 |
| `code-review-checklist` | 编码后审查 | "写完检查什么"的清单 |
| `doc-maintenance` | 文档操作时 | 文档体系的元规则 |
| `fairygui-tools` | UI 开发时 | FairyGUI 全链路 SOP |
| `luban-config` | 配表操作时 | Luban 配置表 SOP |
| `task-tracker` | 跨会话时 | 任务状态持久化 |
| `tdd-pk-review` | 设计评审时 | 多 Agent 对抗机制 |
| `vfx-creator` | 特效开发时 | VFX 工作流 SOP |

**经验**：**Skill = AI 的技能树。** 每个 Skill 就是一个专精方向，按需加载不浪费 context window，又不会在关键时刻缺失知识。

---

### Epoch 8：CodeGraph 代码知识图谱（2026-05-24）

**痛点**：代码检索靠 grep + read_file 暴力搜索，1500+ 文件里找调用链极慢，token 消耗巨大。

**进化**：接入 CodeGraph MCP——基于 tree-sitter 的代码知识图谱，预索引 31K 符号节点 + 57K 关系边。

| 事件 | 产出 | 影响 |
|------|------|------|
| CodeGraph 安装配置 | `.codegraph/` + `~/.workbuddy/mcp.json` | AI 代码检索从多次 grep 降为单次图查询 |
| TOOLS/CODEGRAPH_INTEGRATION.md | `Docs/Agent/` | ~60% token 节省 + ~50% 响应时间缩短 |

**经验**：**给 AI 一张代码地图，胜过让它一条一条路试。** 预索引的知识图谱让"理解代码关系"从 O(n) 变成 O(1)。

---

### Epoch 9：记忆精简与知识迁移（2026-05-24）

**痛点**：MEMORY.md 膨胀到 80+ 行，充斥着编码细节（哪个字段用什么类型、哪个 PIT 编号对应什么坑）。真正战略级的信息被淹没。

**进化**：
1. 编码铁律/踩坑经验/FairyGUI 规则全部迁移到对应 Skill 的 `references/`
2. MEMORY.md 精简到 55 行，只保留战略级信息（方向/架构/协作偏好）
3. Skill 文件本身也做了瘦身（SKILL.md ≤150 行，详细内容下沉到 `references/`）

| 事件 | 提交 | 影响 |
|------|------|------|
| Skill 瘦身 | `5cca8cb` | 总行数从 ~1700 降到 ~300（-80%），按需加载 |
| 编码规则迁移 | `4f6395a` | MEMORY 从 80→55 行，Skill 成为规则的唯一数据源 |

**经验**：**AI 的记忆也需要"断舍离"。** 战略放记忆里，战术放 Skill 里，细节放 references/ 里——三级缓存让 AI 既快又深。

---

### Epoch 10：文档合一（Epoch 1 的进化）

**痛点**：双轨制（Agent/ + Guide/）维护成本太高——改一处要同步两处，经常不一致。

**进化**：逐步将人类文档和 Agent 文档合并为统一格式。Agent/ 文档本身已经足够结构化且可读。`Guide/` 逐渐被弱化，核心内容都收归 `Agent/`。

**经验**：**好的 Agent 文档本身就是好的人类文档。** 结构化 + 字段精确 + 可检索 = 机器和人类都满意。双轨制是过渡期方案，统一是终极形态。

## 进化规律总结

### 🔁 模式一：痛点驱动

```
发现痛点 → 设计方案 → 落地实施 → 沉淀为机制
```

每一次进化都始于一个具体的、反复出现的痛苦。不是"应该这样做"，而是"不这样做太痛了"。

### 📈 模式二：逐层抽象

```
手动操作 → 文档化 → 脚本化 → Skill 化 → 架构化
```

知识的固化程度逐步加深：从口头约定到写下来，到自动化脚本，到可加载的 Skill，最终成为架构的一部分。

### ⚖️ 模式三：先膨胀后收敛

```
积累（信息膨胀）→ 到达临界点（太乱/太长/太重）→ 重组（拆分/迁移/精简）
```

MEMORY、文档、Skill 都经历了先膨胀后收敛的周期。这不是失败——这是必要的探索过程。

### 🤝 模式四：人机协同设计

每次进化都是天命人设计+AI 执行的协作：
- **天命人**：发现痛点、设计机制、决定方向
- **AI**：实施落地、维护规则、积累经验
